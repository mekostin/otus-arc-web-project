# 0002. Feature-Sliced Design как архитектура фронтенда

- **Status:** Accepted
- **Date:** 2026-08-01
- **Deciders:** Михаил Костин (программист 3-й категории)

## Context

Фронтенду нужна внутренняя структура: где проходят границы между частями кода и
как ограничить направление зависимостей, чтобы изменение в одном месте не
расползалось по всему проекту. У платформы уже несколько доменов (из
[`../04-decomposition.md`](../04-decomposition.md): контент, подписки,
идентификация), и без явных границ фронтенд со временем превращается в код, где
всё зависит от всего. Определяющий атрибут — **Модифицируемость** из
[`../01-quality-attributes.md`](../01-quality-attributes.md).

Сравниваемые подходы к декомпозиции:

- **Layered** — граница по типу файла (components/services/api); просто, но папка
  services со временем растёт бесконтрольно.
- **Feature-based** — граница по домену/фиче; логично, но без формальных правил
  зависимостей.
- **FSD (Feature-Sliced Design)** — 6 слоёв (App → Pages → Widgets → Features →
  Entities → Shared) + правило Public API; строгие границы ценой дисциплины.

## Decision

Выбираем **FSD без преждевременного усложнения**: берём слои и правило Public API
(`index.ts`), импорт только из нижних слоёв; сегменты и Clean Architecture внутри
срезов вводим только там, где фича действительно стала сложной. Детали разложения — в
[`../06-frontend-architecture.md`](../06-frontend-architecture.md).

## Consequences

**Что выигрываем.**

- Явные границы и Public API: изменение внутри среза не расползается, снаружи виден
  только контракт — прямой вклад в Модифицируемость.
- Слой `entities` выровнен с владельцами данных из DDD-декомпозиции — структура
  кода совпадает со структурой домена.
- Граница редактора в FSD совпадает с точкой code splitting из
  [`../05-rendering-delivery.md`](../05-rendering-delivery.md) — модифицируемость и
  производительность тянут в одну сторону.

**Чем платим.**

- Требуется дисциплина (Public API, направление импортов) и статическая проверка
  циклов (`import/no-cycle`).
- Риск overengineering на команде из одного человека снижаем тем, что не вводим
  сегменты и Clean-слои заранее.

**Что отвергли.**

- **Layered** — на нескольких доменах папка services расползается, граница по типу
  файла не удерживает рост.
- **Feature-based** — режет по домену, но не фиксирует направление зависимостей и
  Public API; границы держатся на договорённости, а не на правиле.
- **Полный FSD с сегментами и Clean Architecture сразу** — преждевременная
  сложность для текущего масштаба; конспект прямо называет это антипаттерном.
