# 0003. Фронтенд-монолит вместо микрофронтендов

- **Status:** Accepted
- **Date:** 2026-08-01
- **Deciders:** Михаил Костин (программист 3-й категории)

## Context

Нужно выбрать, оставляем ли фронтенд одним приложением или делим его на
микрофронтенды с независимым деплоем. Для публичного сайта важен драйвер **D4**:
если одна часть интерфейса падает и ломает страницу, мы теряем трафик. Подробное
обоснование решения — в
[`../06-frontend-architecture.md`](../06-frontend-architecture.md).

Сравниваемые варианты (ось деплоя):

- **Микрофронтенды** (напр. через Module Federation) — части продукта деплоятся
  независимыми командами по отдельности.
- **Фронтенд-монолит** — одно приложение, одна сборка, единый деплой; внутренние
  границы держит FSD ([ADR 0002](0002-frontend-fsd.md)).

## Decision

Фронтенд остаётся одним приложением в одном репозитории и выкатывается одним
деплоем. Внутренние границы держим через FSD; микрофронтенды и отдельный
monorepo-инструментарий сейчас не используем.

## Consequences

**Что выигрываем.**

- Одна сборка и один деплой проще в поддержке, чем набор отдельно загружаемых
  частей интерфейса.
- Доступность не перемножается: если страница зависит от нескольких отдельно
  загружаемых частей, отказ любой из них ломает сценарий. У монолита нет этой
  дополнительной зависимости между частями, что лучше для D4.
- Простота эксплуатации под текущий масштаб — одна команда, один релизный цикл.

**Чем платим.**

- Если появятся автономные команды с разными релизными циклами, решение придётся
  пересмотреть и выделить независимые части фронтенда.

**Что отвергли.**

- **Микрофронтенды сейчас** — четыре проверочных вопроса дают «нет» на все
  (нет нескольких команд-владельцев, нет нужды в независимом релизе сегодня, нет
  DevOps-мощности на инфраструктуру Module Federation, нет совпадения границы с
  командой). При этом они ухудшили бы доступность против D4.
